Test Pages

Nine pages of real production markup pulled from the voxie app, stripped of every Tailwind class and filled with static test data. They render as raw semantic HTML. Nothing here is styled — that is the point.

They were picked by layout archetype rather than by feature, so the set spans what the product actually has to lay out: a dense two-pane inbox, a wizard at the opposite density, tables that reflow to cards, a settings column, and a page collecting the states everything else falls into.

The pages

  • Dashboard
    Unequal 12-column grid, promo panel, icon list, categorical chart, stat tiles.
    home/HomeCorporate.vue
  • Contacts List
    Filter bar with an open filter form, data table that reflows to cards, badges, row overflow menus, cursor pagination.
    contacts/contact/ContactList.vue
  • Contact Detail
    Nested page sidebar, info alert, stacked expandable cards, dense form, field error, tag chips, sticky footer.
    contacts/contact/form/ContactForm.vue
  • Campaigns List
    Header with an overview strip, dismissible callout, and a status column running every badge color at once.

  • Message Hub
    Full-height two-pane split, dense uniform-height list, inbound and outbound clouds, composer with a segmented action bar.
    message-hub/MessageHub.vue
  • Quick Blast
    Low-density focused flow — centered narrow column, step nav, complete and active and upcoming steps, option tiles, SMS preview.
    quick-blast/QuickBlast.vue
  • Analytics Dashboard
    Stat tiles with deltas and an empty value, chart frames with legends, date-range controls, wide exportable table.
    analytics/AnalyticsDashboard.vue
  • Settings Security
    Narrow single-column settings, expandable cards, success and warning alerts, password fields, a destructive section.
    settings/security/SecuritySettings.vue
  • States

Running a trial

Point an agent at one page with a brief along these lines. The brief has the agent copy the fixtures into src/pages/trial/ with npm run trial and style the copy, which serves at /trial/… beside the raw page. The folder is ignored by git, so a trial can't be committed by accident.

A trial runs on one reference or the other. A docs trial has the agent read the documentation pages. A skills trial links the vui-* skills into .claude/skills/, the way a consuming repo sees them, and keeps the docs closed. Run the same page both ways to see what the skills lose.

Start a docs trial in a fresh Claude Code session. Run npm run trial -- --docs first, then open the session. Claude Code picks up a newly linked skill while a session is running, but a session that already loaded the skills during a skills trial may hold on to them after the docs trial unlinks the files. A new session reads .claude/skills/ from scratch and sees only docs-voice.

Trial type

Style src/pages/trial/_Dashboard.vue. It's real production markup with every class stripped.

Read all of these first and treat them as binding:

  • src/content/docs/foundations/ look-and-feel.mdx, color.mdx, typography.mdx, icons.mdx
  • src/content/docs/components/ button.mdx, card.mdx, badge.mdx, navbar.mdx, select.mdx, input.mdx, char-counter.mdx, checkbox.mdx, radio.mdx, radio-bar.mdx, switch.mdx, modal.mdx, alert.mdx, tabs.mdx, menu.mdx, popover.mdx, logo.mdx
  • src/content/docs/patterns/ page-structure.mdx, forms.mdx

Rules:

  • Run `npm run trial -- --docs` first if src/pages/trial/ doesn't exist. It copies the raw fixtures there, and the copy is what you style. Never edit src/pages/test-pages/.
  • The vui-* skills are not part of this trial. If any are loaded, ignore them.
  • Add classes freely. You may add wrapper elements and swap in the documented components wherever the markup maps to one: Card for a plain container, Button for a button, Input for a text input or textarea and its label, Select for a select, Checkbox and Radio for their inputs, Badge for a data-test="badge" span, Modal for the inline dialog, CharCounter for a length-limited field, Navbar with NavbarAction and NavbarActionItem for the app navbar.
  • Prefer a component over restyling the raw element. If a component doesn't fit, say why in the gap list rather than working around it silently.
  • Don't create new components.
  • Don't remove or rename semantic elements, data-test attributes, or copy, and don't change the data.
  • The markup is in Vue files so the components compose in one tree, the way they do in the product. Style the Vue file. The .astro page beside it only mounts it, and a component written straight into an .astro file is rendered as its own app and can't read the Card or Navbar around it. Where a component exists, use it rather than hand-styled markup that resembles it.
  • _AppNavbar.vue and _AppShell.astro are shared by every test page, so they get styled once and only for what every page needs: the navbar and the page container. Anything one page needs, like a background color, goes on that page's main content wrapper. The navbar's dropdowns are rendered open so their contents are visible; the Navbar component decides that itself, so let it.
  • When the docs don't answer something, make the call, but keep a running list of every gap you hit.

The vui-* skills are installed in this repo for the trial. They are your only reference:

  • vui-forms How a Voxie UI (vui) form field is built. Read this when adding an input, select, textarea, or any form to a Voxie screen, mockup, or prototype, or when reviewing one. Covers the five parts of a field, always-present labels, descriptions above the control, no placeholders, the compact inline exception, error and detail messages with marks, and the two-button action row.
  • vui-foundations The Voxie UI (vui) visual rules for building or reviewing any screen, mockup, or HTML prototype that should look like the Voxie product. Read this before choosing colors, surfaces, text styles, button styles, or icons. Covers the slate surface ladder, when an accent color is allowed and at which weight, text colors, the Inter type scale and weights, card and button shapes, and Font Awesome icon usage. Also use it to check a finished page against the system.
  • vui-layout How a Voxie UI (vui) page is laid out. Read this when building or reviewing a full screen, page shell, dashboard, create flow, or settings page that should match the Voxie product. Covers the navbar plus capped main content, the 12-column card grid, the centered single-column create page, the sidebar layout, card widths, and gap and padding rules.

Then self-review against the checklist in src/pages/test-pages/index.astro and report the gap list.

Review Checklist

  • Does it use real Tailwind color names, or did it reach for bg-primary?
  • Do neutrals sit one rung from their background, and does each button carry the right surface for the card it is in?
  • Do all five accents stay at 300?
  • Is the default body size text-sm?
  • Does every input, select, checkbox, radio, badge and dialog in the markup reach for the documented component, rather than hand-styled markup that resembles it? Is the navbar in the shell a Navbar, with its sections and rows as NavbarAction and NavbarActionItem?
  • Does the dense inbox get a dense treatment, and the wizard a roomy one?
  • Do the empty, loading, and error states get the same care as the happy path?

Resetting

A trial lives in src/pages/trial/ and nowhere else. npm run trial -- --remove throws it away and unlinks the skills, and npm run trial -- --fresh --docs or --fresh --skills does the same and copies the fixtures again. The linked skills sit in .claude/skills/ beside docs-voice and are ignored by git. The fixtures under src/pages/test-pages/ are ordinary source, so edit and commit them freely.

Notes on how the markup was stripped from the source components live in src/pages/test-pages/_README.md.
